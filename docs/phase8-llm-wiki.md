# Phase 8 — 메모 + LLM 위키 + MCP (상세 설계)

> 이 문서는 `ROADMAP.md`의 Phase 8과 `.cursor/prd.md` D53의 **구현용 상세 스펙**이다.
> ROADMAP/PRD는 요약·결정만 담고, 구현 시 필요한 세부(데이터 모델, 알고리즘, 프롬프트, UI 상태, 엣지 케이스)는 이 문서를 정본으로 참조한다.
> 최종 업데이트: 2026-09-02 (설계 확정 · 미구현 · **미결 질문 OW1~OW6 전부 확정, 착수 준비 완료**)

---

## 1. 배경과 목표

Andrej Karpathy의 **"LLM wiki"** 패턴(원문: gist 442a6bf…)을 **비개발자(직장인·사무직·학생)** 대상으로 재해석한다.

- **RAG의 한계:** 대부분의 앱은 질문할 때마다 raw 문서에서 조각을 다시 찾아 조합한다. 지식이 **누적되지 않는다.**
- **LLM wiki의 핵심:** LLM이 **지속적으로 유지되는 위키**(서로 연결된 MD 문서 모음)를 만들고 갱신한다. 지식은 **한 번 컴파일되고 계속 최신화**된다.
- **Campsis의 재해석:** Karpathy 버전은 "Obsidian + Claude Code + 사람이 스키마·큐레이션·유지보수" 를 전제한다. 우리는 그 **사람의 역할을 자동화·비가시화**하고, Obsidian/CLI 자리를 **ChatGPT식 채팅 UI**로 대체한다.

**차별점(해자):** "위키 = 태그 폴더"가 아니라 **소속 메모들을 종합한 문서**라는 점. 소스가 쌓일수록 위키가 스스로 풍부해지고, 채팅 답변이 깊어지고, MCP로 내보낼 고신호 지식이 생긴다. 이 "누적 종합"이 없으면 그냥 또 하나의 메모앱이다.

## 2. 개념 모델

사용자에게 보이는 표면은 **메뉴 3개**, "위키 엔진"은 숨긴다.

| 표면 | 정체 | 사용자 인식 |
|---|---|---|
| **메모**(정리본) | raw → MD 개별 노트. 자동 생성·항상 검색됨 | "내가 저장한 것들" |
| **나의 위키** | 토픽 허브 = 소속 메모들을 **종합한** 문서 | "정리된 내 지식" |
| **채팅** | 위키+메모 기반 Q&A | "물어보면 답해주는 곳" |

원칙:
- **메모는 자동·개별, 위키는 사용자가 승격한 것만·종합.**
- **캡처 핫패스에는 어떤 선택 모달도 없다**(⌥Space 무마찰 유지). 위키 승격은 사용자가 여유 있을 때 하는 **별도 배치 작업.**
- 사용자는 "entity page / synthesis / graph" 같은 개발자 용어를 배울 필요가 없다.

## 3. 전체 플로우 (정본)

라벨 규약: **C = 사용자가 보는 승격 행위**, **D = 그 결과 내부 동작**.

### A. 캡처 → 정리본 생성 (자동, 대부분 구현됨)
1. raw 주입: 캡처(선택 텍스트/스크린샷), 빠른 메모, 파일 업로드.
2. 즉시 `Source` 저장(검색 가능).
3. 백그라운드에서 `LunaMarkdownGenerator`가 정리본(MD) 생성 = 제목·요약·태그·본문. 이미지면 Luna 비전이 OCR+이해까지 단일 호출.
4. 정리본을 bge-m3로 임베딩 → 이 시점부터 채팅·검색에 잡힘.
5. 모든 정리본은 일단 **"위키 미주입"** 상태.

### B. 정리본 확인 (메모 메뉴, 부분 구현됨)
1. 정리본 목록·원본 확인(구현됨).
2. 목록을 **"위키 미주입 / 위키 주입됨"** 으로 구분.
   - 주입됨: **소속 위키 배지**("생산성", "회의록").
   - 미주입: **추천 위키 배지**(임베딩 유사도 기반). **OW6 확정: 배지만 표시, 자동 체크 안 함** — 배지는 **T_high 이상 확신 매칭만**(애매하면 배지 없음, 노이즈 방지). "어떤 메모를 올릴지"는 사용자 결정.
3. **부드러운 넛지(옵트인, OW6):** 목록 상단에 가벼운 배너 **"정리 안 된 메모 N개 · 추천 묶음 보기"**. 클릭 시 추천 기준으로 batch 프리필된 채 C.3로 진입(§11 배치 추천과 동일). 자동 실행·자동 커밋 없음. 추천 배지/넛지는 **설정에서 off 가능**.
   - **경계:** "무엇을 올릴지" = 사용자(자동 체크 ✗). "올린 메모가 어디로 갈지" = 시스템 자동 체크(C.3, OW3).

### C. 위키 승격 (핵심 신규 플로우)
- **C.1** 미주입 정리본을 **체크박스로 배치 선택**(전체 선택·토픽 필터 제공).
- **C.2** **"위키에 정리"** 버튼 클릭 (트리거. "생성"이 아님 — 대부분 기존 위키에 추가).
- **C.3** **라우팅 미리보기**(자동 실행 금지, 반드시 이 확인 단계):
  ```
  선택한 5개 → 이렇게 정리할게요
    생산성 (기존)      ← 메모 3개
    회의록 (기존)      ← 메모 2개
    OKR (새로 만들기)  ← 메모 1개   [☐ 만들기]
  [정리 실행]
  ```
  - 각 정리본 토픽을 **기존 위키와 먼저 매칭**(임베딩) → 겹치면 기존으로 유도(토픽 폭발/중복 방지).
  - 매칭 없으면 **새 위키 후보** 제시.
  - 한 메모가 여러 토픽 → 여러 위키 가능. **상위 관련 토픽만 미리 선택**, 나머지 접어둠.
  - 사용자가 목적지 추가/제외/수정 가능.
- **C.4** **"정리 실행"** → D로.

### D. 위키 재합성 (내부 동작)
- **D.1 즉시 반영:** 선택 메모를 각 위키의 **구성원으로 등록**(다대다) + **백링크 생성**. 목록·소속 배지 즉시 갱신 → 사용자는 "정리됨"을 바로 봄.
- **D.2 종합 재작성(즉시 수행, 백그라운드):**
  - **위키별 1회** 재합성(메모마다 X).
  - **증분 방식:** 전체 구성원 재독 금지. **[현재 위키 페이지 + 새로 추가된 메모들]** 만 Luna에 전달해 갱신 → 위키가 커져도 비용 **선형**.
  - `reasoning_effort: low`.
  - 각 위키에 **"정리 중…" 상태 배지**(`markdownStatus` .processing 패턴 재사용), 사용자 비차단.
  - 갱신된 위키 페이지 재임베딩(검색·채팅·MCP 대상).

### E. 나의 위키 메뉴 (열람, 신규)
1. 토픽별 위키 **리스트**(구성 메모 수·최근 갱신).
2. **상세**: 종합 요약 + 핵심 포인트 + 관련 위키(백링크) + 구성 메모 목록(클릭 → 정리본 미리보기).
3. (추후 E2) 백링크 노드 그래프 = 마인드맵/지식 지도. 기본 숨김.

### F. 채팅 (위키+메모 기반, 부분 구현됨)
1. 질문 입력.
2. **검색 순서: 위키 페이지 먼저 → 부족하면 개별 메모 드릴다운.** (위키가 이미 메모를 요약하므로 둘 다 긁으면 중복·비용↑)
3. 답변 출처를 **`위키` / `메모` 배지로 구분**(Phase 3 출처 칩 확장).
4. 위키·메모에 없으면 **웹 검색 폴백**(구현됨).

### G. 사이드바 검색 (Phase 6 확장)
- 검색 대상 = **위키 + 정리본**(의미검색). 현재 정리본만 색인 → **위키 페이지도 색인 대상 추가.**
- "이 검색어로 채팅하기" 브리지 유지.

### H. 유지보수 (Lint) — 관리자 부재 대비 필수 인프라
- 백그라운드 점검: **중복 위키 병합 제안**("생산성" vs "업무효율"), **모순 표시**, **고아/빈약 위키**(구성 메모 1개), 오래된 내용.
- 강제 실행 아님 → **"위키 정리 제안" 카드**로 사용자에게.

### I. MCP — 위키만 노출
- 외부 LLM/에이전트는 **위키 페이지만 read**(raw·개별 메모 미노출).
- 전제: ① 위키 최신·정합(H의 Lint), ② 공개/비공개 **권한 스코핑**.

### 임베딩 일반화 (OW2 확정)
- 위키 **대표 임베딩 = 위키 페이지 임베딩**(centroid 아님). 채팅·MCP 검색이 어차피 페이지 임베딩을 요구하므로 유지 대상이 하나로 통일됨.
- 현재 `embedding` 테이블은 `source_id` 1개당 벡터 1개. **위키 페이지도 임베딩**하려면 `kind` 컬럼(`note`|`wiki`, 기본 `note`) 추가 + `source_id`를 `ref_id` 의미로 일반화(기존 행은 `note`로 마이그레이션). `fetchAll(model:version:)`에 `kind` 필터 추가.
- 매칭·검색에서 note/wiki 임베딩을 함께 다루되 `kind`로 구분(채팅 위키 우선 검색 = `kind='wiki'` 우선).
- **폴백:** 페이지 재합성 전(status=processing) 위키는 페이지 임베딩이 없으므로, 그 구간만 구성 메모 벡터 centroid를 즉석 계산해 대표로 사용. 재합성 완료 시 페이지 임베딩으로 대체.

> 마이그레이션은 기존 v5~v7 패턴(`Migrations.swift`)을 따른다. 새 버전(v8) 부여.

## 5. 승격 & 라우팅 (알고리즘 상세)

### 기존 위키 매칭
1. 정리본 임베딩(이미 있음)을 **각 위키의 대표 임베딩 = 위키 페이지 임베딩**(OW2 확정)과 코사인 비교. 페이지가 아직 없는 신규/재합성 전 위키만 **구성 메모 centroid로 임시 대체**.
2. **태그 겹침**(`source.topics` ∩ 위키 topic)도 보조 신호로 가중.
3. **2단 밴드로 분기(OW3 확정):** 최종 신호 = `0.7·코사인유사도 + 0.3·태그겹침비율`(둘 다 0~1로 정규화).
   - **≥ T_high(0.55):** **자동 선택 목적지**(라우팅 미리보기에서 체크된 상태로 제시).
   - **T_low(0.40) ~ T_high(0.55):** **후보로만 제시(체크 해제 상태)** → 사용자가 고름. (OW1의 "중간 점수" 밴드)
   - **< T_low(0.40):** 후보 아님.
4. **모든 위키가 < T_low** → **강제 편입 금지**, 그 메모의 **대표 토픽으로 새 위키 후보** 생성(OW1 하이브리드: 안 맞는 데이터는 새 위키로 빠져 쏠림 방지).
5. **콜드스타트 동적 조정:** 위키 수에 따라 T_high를 스케일. 위키 **0~2개면 T_high=0.65**(새 위키 유도), **3~4개면 0.60**, **5개+면 기본 0.55**. T_low는 0.40 고정.

### 멀티토픽 상한
- 한 메모가 여러 위키로 갈 수 있으나, **기본 상한 N_max=3** — 비용 곱연산 방지. 초과 시 상위 3개만 미리 선택(체크), 나머지는 접어둠.

### 새 위키 생성 시 중복 방지
- 새 위키 후보 토픽을 기존 위키 `topic_slug`/임베딩과 재비교 → 사실상 동일하면 **"기존 X와 합칠까요?"** 로 유도(Lint의 병합과 동일 로직 재사용).

### UI 상태 (라우팅 미리보기)
- 목적지별 그룹(기존/신규), 각 메모 체크·제외, "새로 만들기" 개별 토글.
- 확정 전에는 아무 변경도 커밋하지 않음.

## 6. 재합성 (프롬프트 & 실행 상세)

### 실행 모델
- **트리거:** C.4 "정리 실행" 즉시(사용자 요청 배치라 비용 통제).
- **그룹핑:** 선택 메모를 **목적지 위키별로 묶어 위키당 1 호출.**
- **백그라운드:** 위키 `markdown_status = .processing` → 완료 시 `.completed` + 재임베딩.

### 증분 재합성 프롬프트(형태 제안)
- system: "너는 개인 지식 위키의 유지관리자다. 기존 위키 페이지에 새 메모들을 **통합**하되, 단순 이어붙이기(append) 금지. 종합·재구성하라. 사실에 충실(환각 금지), 원문 세부(이름·숫자·URL) 보존. 사용자가 직접 편집한 부분은 존중. 새 정보가 기존 내용과 **모순되면 표시**. 출력은 JSON."
- user content:
  ```
  [기존 위키 페이지]
  {현재 markdown}

  [새로 추가된 메모 N개]
  - {메모1 요약/본문}
  - {메모2 …}
  ```
- 출력 JSON: `{ "markdown": string, "summary": string, "related_topics": string[] }`
  - `related_topics` → `wiki_wiki_link` 후보로 사용(기존 위키명과 매칭되면 백링크 생성).

### 새 위키 첫 종합
- 기존 페이지가 없으므로 초기 구성원들만으로 종합. 같은 JSON 스키마.

### 위키 페이지 MD 구조(권장)
```markdown
# {제목}
{종합 요약 2~4문장}

## 핵심 포인트
- …

## 관련 위키
- [[다른 위키]] …        ← wiki_wiki_link

## 구성 메모
- {메모 제목} (YYYY-MM-DD)  ← note_wiki_link, 클릭 시 정리본
```
- (선택) YAML 프론트매터(tags/updated/member_count) → 추후 동적 뷰.

### 비용/성능
- 전체 재합성은 누적 입력이 O(N²)로 폭증 → **반드시 증분.**
- `reasoning_effort: low`, `response_format: json`(현 `LunaMarkdownGenerator`와 동일).
- 1인 사용자 기준 절대 비용은 작음; 대규모/멀티토픽에서 목적지 상한으로 관리.

## 7. 채팅 검색 전략 (상세)

1. 질의 임베딩 → **위키 임베딩 우선 검색**(topN_wiki).
2. 위키 히트가 충분하면 위키 페이지를 컨텍스트로 답변, 출처=위키.
3. 부족하거나 구체 근거 필요 시 **구성 메모/개별 메모 드릴다운**(topN_note), 출처=메모.
4. 관련도 순 정렬 유지(기존 `relevantSources` 로직 확장).
5. 출처 칩에 **`위키`/`메모` 배지** + 클릭 시 각각 위키 상세/정리본 미리보기.
6. 둘 다 부족 → 웹 검색 폴백(구현됨).

## 8. Lint (유지보수, 상세)

| 검사 | 방법 | 결과 |
|---|---|---|
| 중복 위키 | 위키 임베딩 유사도 ≥ T_merge(0.80) **또는** `topic_slug` 정규화 일치 | "합칠까요?" 제안 카드 |
| 모순 | 재합성 시 LLM이 표시한 conflict 수집 | 위키 상단 경고 |
| 고아/빈약 | `member_count ≤ 1` 또는 inbound link 0 | "정리/삭제 제안" |
| stale | 오래 갱신 안 됨 + 관련 새 메모 존재 | "업데이트 제안" |

- **트리거(OW5 확정):** ①위키 메뉴 진입 시 가벼운 로컬 점검(주) ②승격/재합성 완료 직후 해당 위키만 국소 점검(piggyback) ③저빈도 전수 스캔(보조) = 앱 유휴 시 하루 최대 1회(마지막 스캔 +24h & 위키 변경 있었을 때만), `ProcessingQueue` 백그라운드 잡.
- **비용:** Lint 자체는 **LLM 비호출**(중복=벡터, 고아=DB, stale=날짜 → 로컬). 모순만 재합성 piggyback(추가 0). → 주기·비용 우려 없음.
- **알림 절제:** 결과는 항상 **비파괴 제안 카드**(사용자 승인). dismiss한 제안은 **재알림 쿨다운**.
- **MVP 스코프:** ①②만으로 시작, ③ 전수 스캔은 후순위.

---

## 9. MCP (상세)

- 노출 범위: **위키 페이지(종합 MD)만.** raw/개별 메모/원본 파일 미노출.
- 도구 형태: 위키 검색(read) + 위키 페이지 read. (Karpathy가 언급한 qmd-as-MCP와 유사, 단 위키 한정)
- 전제: 위키 신선도(Lint), **공개/비공개 위키 플래그**로 권한 스코핑.
- 이유: 위키는 정제·종합된 고신호 + 프라이버시 안전 레이어라 외부 노출에 최적.

## 10. 신뢰 · 안전

- **사람 편집 보호:** 사용자가 위키 페이지를 편집하면 `markdown_edited = true` → 자동 재합성이 덮어쓰기 전 확인(정리본의 기존 로직을 위키로 확장).
- **되돌리기(OW4 확정): MD 스냅샷 방식**(git 유사 이력 아님 — 비개발자에겐 과잉). **규칙:** 위키 MD에 쓰기 직전 이전 버전을 스냅샷(재합성·편집·승격 공통). 위치 `AppPaths/wiki_revisions/{wikiId}/{revisionId}.md`, 메타 테이블 `wiki_revision`(§4). 위키당 최근 N=10 링버퍼. 되돌리기 = 직전 MD 복원 + 재임베딩(+ 승격이면 `added_source_ids`의 링크 제거·`member_count` 복구). UI: 완료 토스트에 원클릭 "되돌리기", 위키 상세 "기록"은 후순위.
- **환각 억제:** 프롬프트 충실성 규칙, 구성 메모로 출처 추적 가능.
- **투명성:** "이 위키는 메모 N개로 만들어졌어요" + 구성 메모 링크 상시 노출.

## 11. 엣지 케이스

- **메모 삭제/언링크:** 소속 위키의 `member_count` 감소 → 필요 시 재합성(다음 승격/열람/lint 때). 구성원 0이면 고아 위키 → 삭제/보관 제안.
- **위키 삭제:** `note_wiki_link` 정리, 메모는 그대로(메모는 위키와 독립).
- **콜드스타트:** 메모 1~2개는 위키 없이 자연스러움. 사용자가 명시적으로 승격하면 1개로도 새 위키 생성 가능(명시적 의도).
- **대량 선택:** 미주입 200개 → 전체 선택/토픽 필터/추천 배치("이 12개는 '생산성'으로").
- **멀티멤버십:** "주입됨"은 최종 아님 — 다른 위키에 추가 가능, 각 메모에 소속 위키 배지.

## 13. 설계 결정 (구 미결 질문 OW1~OW6 — 2026-09-02 전부 해소)

> 이 섹션은 원래 **착수 전 확정이 필요한 미결 질문(Open Questions)** 이었으나, 2026-09-02 대화로 OW1~OW6 전부 확정되었다. OW 라벨은 추적용으로 유지하고, 각 항목 앞에 결론을 명시한다. (기존안은 취소선으로 보존)

- **OW1. 토픽 체계 — 확정(2026-09-02): 임계값 기반 하이브리드.** ~~(A) 완전 발현형 vs (B) 반통제형, 잠정 B로 시작~~ → 순수 B는 폐기(사용자가 어떤 성격의 데이터를 넣을지 모르는데 기존 위키에 강제 편입하면 주제가 한쪽으로 쏠림·왜곡). 대신 **정리본 임베딩 ↔ 기존 위키 유사도의 임계값(T_match)으로 A/B를 자동 분기**한다:
  - **유사도 ≥ T_match** → 기존 위키 편입 제안(B의 장점: 깔끔·중복 방지).
  - **여러 위키에 중간 점수** → 후보 K개 제시, 사용자 선택.
  - **어디에도 < T_match** → **강제 편입 금지, "새 위키 만들기" 제안**(A의 장점: 쏠림·왜곡 방지). 새 위키 확정은 라우팅 미리보기(C.3)의 명시적 사용자 승인 지점.
  - **콜드스타트 완화:** 위키 0~2개일 땐 T_match를 높게 잡아 새 위키가 잘 생기게(초반 다양화), 성숙하면 낮춰 편입 유도.
  - **쏠림 안전장치:** 한 위키에 메모 과다 집중 시 Lint가 "쪼갤까요?"(발현형 세분화를 사후에 얹음).
  - 상세 매칭·임계값은 §5·OW3 참조.
- **OW2. 위키 대표 임베딩 — 확정(2026-09-02): 위키 페이지 임베딩.** ~~페이지 임베딩 vs 구성 메모 centroid~~ → 페이지 임베딩 채택. 근거: ①채팅·MCP가 어차피 페이지 임베딩을 요구 → 추가 인프라 0, 유지 대상 단일화. ②위키는 "메모 평균"이 아니라 "종합 문서"이므로 그 문서 임베딩이 의미상 정확. ③centroid는 멀티토픽 위키에서 drift(평균이 빈 공간에 착지)해 매칭 저하. ④페이지는 요약이라 bge-m3 8k 토큰 안에 들어가 truncation 위험 낮음. **폴백:** 재합성 전 위키만 구성 메모 centroid 임시 사용. 스키마는 §4(`kind` 컬럼 추가), 잔여 drift는 OW3 태그겹침 신호+T_low 밴드로 완화.
- **OW3. 임계값 — 확정(2026-09-02).** 기준: 현행 앱 bge-m3 코사인 스케일(채팅 관련성 하한 0.4, 일반 검색 0.3, 의미검색 0.25). 모든 값은 **초기값**이며 `match_score`(note_wiki_link) 로그로 사후 튜닝.
  - **매칭 신호:** `0.7·코사인 + 0.3·태그겹침비율`(§5).
  - **T_high = 0.55**(자동 선택), **T_low = 0.40**(후보 제시 하한, 채팅 relevanceFloor와 정렬). 사이 밴드 = 사용자 선택.
  - **콜드스타트:** T_high를 위키 수로 스케일(0~2개 0.65 / 3~4개 0.60 / 5+ 0.55). T_low 고정.
  - **T_merge = 0.80**(위키↔위키 병합 제안) 또는 `topic_slug` 정규화 일치. 병합은 파괴적이라 보수적 고값.
  - **N_max = 3**(한 메모의 목적지 위키 상한, 재합성 비용 곱연산 방지).
  - **튜닝 방법:** 값들을 한 곳(상수/설정)에 모아 관리(현 `relevanceFloor`/`relativeMargin` 패턴). 라우팅 미리보기의 사용자 수락/거절이 곧 라벨 → 승격 시 `match_score` 저장 후, 수락 vs 거절 분포를 보고 T_high/T_low 재조정. 데이터 없기 전엔 보수적 유지 + 사용자가 미리보기에서 교정.
- **OW4. 되돌리기 저장 방식 — 확정(2026-09-02): MD 스냅샷.** ~~스냅샷 vs git 유사 이력~~ → 스냅샷 채택(git 유사 이력은 비개발자에게 과잉·취약, §10 요구는 "원클릭 되돌리기"지 VCS 아님). 위키 MD 쓰기 직전 이전 버전을 `wiki_revision` 테이블+`wiki_revisions/{wikiId}/{id}.md`로 보관, 위키당 최근 N=10 링버퍼. 되돌리기=직전 MD 복원+재임베딩(승격이면 `added_source_ids` 링크 제거·member_count 복구). 상세 §4·§10. (MD 수 KB라 디스크 부담 무시 가능)
- **OW5. Lint 트리거 주기 — 확정(2026-09-02): 이벤트 기반 국소(주) + 저빈도 전수(보조), LLM 비호출.** 시점: ①위키 메뉴 진입 ②승격/재합성 완료 직후 해당 위키 ③앱 유휴 시 하루 최대 1회 전수(마지막+24h & 변경 있을 때). 비용: 중복(벡터)·고아(DB)·stale(날짜)은 로컬 → 0, 모순은 재합성 piggyback → 추가 0(별도 LLM Lint 잡 없음). 결과는 비파괴 제안 카드 + dismiss 쿨다운. MVP는 ①② 우선, ③ 후순위. 상세 §8.
- **OW6. 자동 추천 강도 — 확정(2026-09-02): 배지만 표시(자동 체크 ✗) + 옵트인 넛지.** 쟁점은 **메모 목록(B단계)** 에서 "어떤 메모를 올릴지"였음(C.3의 "어디로 갈지" 자동 체크는 OW3에서 이미 확정). 결정: 메모 목록에선 **T_high 이상 확신 매칭만 추천 배지 표시, 프리셀렉트 안 함**(§2 "위키는 사용자가 승격한 것만" 원칙 준수). 사장·콜드스타트 위험은 **"정리 안 된 메모 N개 · 추천 묶음 보기" 옵트인 배너**로 완화(클릭 시 batch 프리필→C.3, 자동 커밋 없음). 배지/넛지 설정 off 가능. **경계 원칙:** 무엇을 올릴지=사용자, 어디로 갈지=시스템(C.3).
