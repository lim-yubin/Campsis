## 배경

로컬 모델(Qwen3-4B)이 사용자 하드웨어를 과도하게 사용하고 품질도 아쉬워,
**생성은 클라우드(GPT-5.6 Luna), 임베딩·검색은 로컬(bge-m3)** 하이브리드로 전환했다.
이 결정에서 "제작자 키를 어떻게 안전하게 쓸까"라는 질문이 파생되어
플랜·서버·배포 전략까지 정리하게 되었다.

## 1. 키 관리 (구현 완료)

### 원칙
- 제작자 키를 앱 번들에 심는 것은 **유출 · 비용 폭탄 · OpenAI 약관 위반**으로 불가.
- 애플 키체인은 "제작자 키 배포" 해결책이 **아니다**. 사용자 기기별 로컬 저장소일 뿐이다.

### 구현: `AICredentials` 계층 리졸버
우선순위대로 키를 해석한다.

1. **사용자 키체인 (BYOK)** — 모든 빌드에서 최우선
2. **(DEBUG 전용) 로컬 `.env`** — 개발 편의용, `#if DEBUG`로 릴리즈 빌드에서 컴파일 제외
3. **(미래) 프록시 서버** — 클라이언트는 키를 직접 갖지 않고 서버가 제작자 키를 보관

> 릴리즈 바이너리에는 `.env` 로더가 컴파일되지 않으므로 제작자 키가 절대 포함되지 않는다.

관련 파일: `Campsis/Campsis/AICredentials.swift`, `KeychainHelper.swift`

## 2. 요금 플랜 (설계 방향)

3-티어 구조. **키가 어디에 있느냐**가 핵심 차이다.

| 플랜 | 키 위치 | 서버 | 과금 | 로그인 |
|---|---|---|---|---|
| **BYOK** (사용자 키) | 사용자 기기 | 불필요 | 사용자 부담 | 불필요 |
| **Free** (내 키, 제한 모델) | 내 서버 | 필수 | 무료 + 쿼터 | 필요 |
| **Pro** (내 키, 고급 모델) | 내 서버 | 필수 | 구독료 | 필요 + 결제 |

**핵심:** Free·Pro는 내 키를 쓰므로 **프록시 서버가 반드시 필요**하다.
BYOK만 서버 없이 앱이 직접 OpenAI를 호출한다.

## 3. 서버 구조

Free/Pro에는 다음 4가지가 필요하다.

1. **인증(Authentication)** — 요청 주체 식별 (JWT 등)
2. **구독 검증(Entitlement)** — 클라이언트를 믿지 말고 **서버가** 플랜 판단
3. **쿼터 & 레이트리밋** — Free는 제한 모델 + 사용량 제한, Pro는 고급 모델 허용
4. **미터링/로깅** — 실제 사용량 기록 → 비용 추적 · 남용 탐지

### 스택: Supabase (이미 연결됨)
- **Supabase Auth** — Apple/Google 소셜, 매직링크, JWT 세션
- **Postgres** — 사용자 · 플랜 · 사용량 테이블 (+ RLS)
- **Edge Function** — 제작자 키를 숨기고 프록시 + 쿼터 체크 후 OpenAI 대리 호출

앱 흐름: 로그인 → JWT 키체인 저장 → Free/Pro 호출 시 JWT 첨부 → Edge Function이 플랜·쿼터 확인 후 OpenAI 호출.

## 4. 배포 방식 — App Store 미배포 확정

### 현재 프로젝트 설정
- `ENABLE_APP_SANDBOX = NO`, `ENABLE_HARDENED_RUNTIME = YES`
- → **Developer ID + 노터라이즈(직접 배포)** 에 맞춰져 있음

### App Store를 하지 않는 이유
- App Store는 **App Sandbox 필수** → 핵심 기능인 **AX 기반 "어디서나 텍스트 캡처"가 막힘**
- 결제도 StoreKit 강제(수수료 15~30%)

### 확정 모델: 브라우저 다운로드 + 웹 대시보드

```
[웹사이트] (브라우저)
  ├─ 랜딩 / 다운로드(.dmg)
  ├─ 회원가입 / 로그인
  ├─ 대시보드 (플랜 · 사용량 · 결제관리)
  └─ 결제 (LemonSqueezy / Paddle / Stripe)
        │
        ▼
[Supabase]  인증 + DB + Edge Function(프록시)
        ▲
        │ JWT
[macOS 앱] (브라우저에서 다운로드)
  ├─ 실행 시 로그인 상태 확인
  ├─ 로그인 → 웹 인증 → 딥링크로 토큰 수신
  └─ Free/Pro 호출 시 토큰 첨부 → Edge Function → OpenAI
```

### 데스크톱 로그인 흐름 (딥링크)
1. 앱에서 "로그인" → 기본 브라우저로 `campsis.com/login` 열기
2. 웹에서 로그인 (소셜/이메일)
3. 웹이 `campsis://auth?token=...` 로 앱 재호출 (커스텀 URL 스킴)
4. 앱이 토큰을 키체인에 저장 → 이후 서버 호출에 첨부

> 회원가입 · 결제 · 대시보드는 전부 웹에서 처리 → 앱은 로그인만, 가벼워진다.

### 이 방식의 장점
- **샌드박스 없음** → 전기능 유지
- **결제 수수료 낮음** (LemonSqueezy ~5% vs 애플 15~30%)
- **업데이트 자유** → Sparkle로 자동 업데이트, 심사 대기 없음
- 회원가입/대시보드/결제가 웹에 집중 → 앱 단순

### App Store를 안 해도 필요한 것
1. **노터라이즈** — 필수 (Developer ID + `notarytool`). 안 하면 실행 차단 경고
2. **자동 업데이트** — Sparkle 프레임워크
3. **다운로드 호스팅** — .dmg 배포처 (S3 / Cloudflare R2 등)

## 5. 권장 로드맵

1. **지금:** BYOK로 먼저 출시 (서버 0원, 제품 검증). ← 클라이언트 거의 완성
2. **다음:** Supabase Auth + Edge Function 프록시 → **Free 티어** (소셜 로그인 하나로 마찰 최소화)
3. **그 다음:** 결제 붙여 **Pro 티어** (LemonSqueezy 등)
4. **나중에:** 웹 대시보드 고도화

> **과설계 경고:** 사용자 없는 단계에서 회원가입·대시보드·결제를 전부 만들면 검증이 늦어진다.
> BYOK 우선 출시 후 수요가 보이면 서버(Free/Pro)를 붙인다.

## 6. business-plan.md와의 차이 (갱신 필요 지점)

기존 `business-plan.md`는 "100% 로컬 / 서버 비용 0 / 클라우드 AI는 Pro 프록시" 전제로 작성됨.
이번 결정으로 다음이 바뀌었으니 추후 반영 필요:

- 생성 기본값이 로컬 → **클라우드(Luna) 하이브리드**로 이동
- 플랜에 **BYOK 티어 추가** (기존엔 Free/Pro/Pro+)
- "서버 비용 0" → Free/Pro는 **프록시 서버 비용 발생** (쿼터로 통제)
- 클라우드 AI 후보(Claude/GPT-4o/Gemini) → **GPT-5.6 Luna**로 구체화
