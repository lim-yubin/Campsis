# Phase 8 — 메모 + LLM 위키 + MCP (상세 설계)

> 이 문서는 `ROADMAP.md`의 Phase 8과 `.cursor/prd.md` D53의 **구현용 상세 스펙**이다.
> ROADMAP/PRD는 요약·결정만 담고, 구현 시 필요한 세부(데이터 모델, 알고리즘, 프롬프트, UI 상태, 엣지 케이스)는 이 문서를 정본으로 참조한다.
> 최종 업데이트: 2026-09-02 (설계 확정 · 미구현)

---

## 1. 배경과 목표

Andrej Karpathy의 **"LLM wiki"** 패턴(원문: gist 442a6bf…)을 **비개발자(직장인·사무직·학생)** 대상으로 재해석한다.

- **RAG의 한계:** 대부분의 앱은 질문할 때마다 raw 문서에서 조각을 다시 찾아 조합한다. 지식이 **누적되지 않는다.**
- **LLM wiki의 핵심:** LLM이 **지속적으로 유지되는 위키**(서로 연결된 MD 문서 모음)를 만들고 갱신한다. 지식은 **한 번 컴파일되고 계속 최신화**된다.
- **Campsis의 재해석:** Karpathy 버전은 "Obsidian + Claude Code + 사람이 스키마·큐레이션·유지보수" 를 전제한다. 우리는 그 **사람의 역할을 자동화·비가시화**하고, Obsidian/CLI 자리를 **ChatGPT식 채팅 UI**로 대체한다.

**차별점(해자):** "위키 = 태그 폴더"가 아니라 **소속 메모들을 종합한 문서**라는 점. 소스가 쌓일수록 위키가 스스로 풍부해지고, 채팅 답변이 깊어지고, MCP로 내보낼 고신호 지식이 생긴다. 이 "누적 종합"이 없으면 그냥 또 하나의 메모앱이다.

## 2. 개념 모델

사용자에게 보이는 표면은 **메뉴 3개**, "위키 엔진"은 숨긴다.

| 표면 | 정체 | 사용자 인식 |
|---|---|---|
| **메모**(정리본) | raw → MD 개별 노트. 자동 생성·항상 검색됨 | "내가 저장한 것들" |
| **나의 위키** | 토픽 허브 = 소속 메모들을 **종합한** 문서 | "정리된 내 지식" |
| **채팅** | 위키+메모 기반 Q&A | "물어보면 답해주는 곳" |

원칙:
- **메모는 자동·개별, 위키는 사용자가 승격한 것만·종합.**
- **캡처 핫패스에는 어떤 선택 모달도 없다**(⌥Space 무마찰 유지). 위키 승격은 사용자가 여유 있을 때 하는 **별도 배치 작업.**
- 사용자는 "entity page / synthesis / graph" 같은 개발자 용어를 배울 필요가 없다.

## 3. 전체 플로우 (정본)

라벨 규약: **C = 사용자가 보는 승격 행위**, **D = 그 결과 내부 동작**.

### A. 캡처 → 정리본 생성 (자동, 대부분 구현됨)
1. raw 주입: 캡처(선택 텍스트/스크린샷), 빠른 메모, 파일 업로드.
2. 즉시 `Source` 저장(검색 가능).
3. 백그라운드에서 `LunaMarkdownGenerator`가 정리본(MD) 생성 = 제목·요약·태그·본문. 이미지면 Luna 비전이 OCR+이해까지 단일 호출.
4. 정리본을 bge-m3로 임베딩 → 이 시점부터 채팅·검색에 잡힘.
5. 모든 정리본은 일단 **"위키 미주입"** 상태.

### B. 정리본 확인 (메모 메뉴, 부분 구현됨)
1. 정리본 목록·원본 확인(구현됨).
2. 목록을 **"위키 미주입 / 위키 주입됨"** 으로 구분.
   - 주입됨: **소속 위키 배지**("생산성", "회의록").
   - 미주입: **추천 위키 배지**(임베딩 유사도 기반) 미리 제시.

### C. 위키 승격 (핵심 신규 플로우)
- **C.1** 미주입 정리본을 **체크박스로 배치 선택**(전체 선택·토픽 필터 제공).
- **C.2** **"위키에 정리"** 버튼 클릭 (트리거. "생성"이 아님 — 대부분 기존 위키에 추가).
- **C.3** **라우팅 미리보기**(자동 실행 금지, 반드시 이 확인 단계):
  ```
  선택한 5개 → 이렇게 정리할게요
    생산성 (기존)      ← 메모 3개
    회의록 (기존)      ← 메모 2개
    OKR (새로 만들기)  ← 메모 1개   [☐ 만들기]
  [정리 실행]
  ```
  - 각 정리본 토픽을 **기존 위키와 먼저 매칭**(임베딩) → 겹치면 기존으로 유도(토픽 폭발/중복 방지).
  - 매칭 없으면 **새 위키 후보** 제시.
  - 한 메모가 여러 토픽 → 여러 위키 가능. **상위 관련 토픽만 미리 선택**, 나머지 접어둠.
  - 사용자가 목적지 추가/제외/수정 가능.
- **C.4** **"정리 실행"** → D로.

### D. 위키 재합성 (내부 동작)
- **D.1 즉시 반영:** 선택 메모를 각 위키의 **구성원으로 등록**(다대다) + **백링크 생성**. 목록·소속 배지 즉시 갱신 → 사용자는 "정리됨"을 바로 봄.
- **D.2 종합 재작성(즉시 수행, 백그라운드):**
  - **위키별 1회** 재합성(메모마다 X).
  - **증분 방식:** 전체 구성원 재독 금지. **[현재 위키 페이지 + 새로 추가된 메모들]** 만 Luna에 전달해 갱신 → 위키가 커져도 비용 **선형**.
  - `reasoning_effort: low`.
  - 각 위키에 **"정리 중…" 상태 배지**(`markdownStatus` .processing 패턴 재사용), 사용자 비차단.
  - 갱신된 위키 페이지 재임베딩(검색·채팅·MCP 대상).

### E. 나의 위키 메뉴 (열람, 신규)
1. 토픽별 위키 **리스트**(구성 메모 수·최근 갱신).
2. **상세**: 종합 요약 + 핵심 포인트 + 관련 위키(백링크) + 구성 메모 목록(클릭 → 정리본 미리보기).
3. (추후 E2) 백링크 노드 그래프 = 마인드맵/지식 지도. 기본 숨김.

### F. 채팅 (위키+메모 기반, 부분 구현됨)
1. 질문 입력.
2. **검색 순서: 위키 페이지 먼저 → 부족하면 개별 메모 드릴다운.** (위키가 이미 메모를 요약하므로 둘 다 긁으면 중복·비용↑)
3. 답변 출처를 **`위키` / `메모` 배지로 구분**(Phase 3 출처 칩 확장).
4. 위키·메모에 없으면 **웹 검색 폴백**(구현됨).

### G. 사이드바 검색 (Phase 6 확장)
- 검색 대상 = **위키 + 정리본**(의미검색). 현재 정리본만 색인 → **위키 페이지도 색인 대상 추가.**
- "이 검색어로 채팅하기" 브리지 유지.

### H. 유지보수 (Lint) — 관리자 부재 대비 필수 인프라
- 백그라운드 점검: **중복 위키 병합 제안**("생산성" vs "업무효율"), **모순 표시**, **고아/빈약 위키**(구성 메모 1개), 오래된 내용.
- 강제 실행 아님 → **"위키 정리 제안" 카드**로 사용자에게.

### I. MCP — 위키만 노출
- 외부 LLM/에이전트는 **위키 페이지만 read**(raw·개별 메모 미노출).
- 전제: ① 위키 최신·정합(H의 Lint), ② 공개/비공개 **권한 스코핑**.

## 4. 데이터 모델 (상세)

기존: `source`(raw+정리본 MD), 임베딩은 `EmbeddingRepository`(현재 `sourceId` 키). 신규 3개 + 임베딩 일반화.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | TEXT PK | UUID |
| `title` | TEXT | 위키 제목(=토픽 대표명) |
| `topic_slug` | TEXT | 정규화 키(중복 매칭·병합용) |

### 임베딩 일반화 (구현 고려사항)
- 현재 `EmbeddingRepository`는 `sourceId` 기준. **위키 페이지도 임베딩**하려면 키를 `(kind: note|wiki, refId)` 또는 별도 `wiki_embedding`으로 확장 필요.
- 매칭·검색에서 note 임베딩과 wiki 임베딩을 함께 다뤄야 하므로 초기에 스키마를 잡아둘 것.

> 마이그레이션은 기존 v5~v7 패턴(`Migrations.swift`)을 따른다. 새 버전(v8) 부여.

## 5. 승격 & 라우팅 (알고리즘 상세)

### 기존 위키 매칭
1. 정리본 임베딩(이미 있음)을 **각 위키의 대표 임베딩**(위키 페이지 임베딩 또는 구성 메모 임베딩 centroid)과 코사인 비교.
2. **태그 겹침**(`source.topics` ∩ 위키 topic)도 보조 신호로 가중.
3. 유사도 ≥ **임계값 T_match**(초기 제안 0.5, 튜닝 대상)인 위키를 후보로, 상위 K개 제시.
4. 임계값 넘는 위키가 하나도 없으면 → 그 메모의 **대표 토픽으로 새 위키 후보** 생성.

### 멀티토픽 상한
- 한 메모가 여러 위키로 갈 수 있으나, **기본 상한 N_max(제안 3)** — 비용 곱연산 방지. 초과 시 상위만 미리 선택.

### 새 위키 생성 시 중복 방지
- 새 위키 후보 토픽을 기존 위키 `topic_slug`/임베딩과 재비교 → 사실상 동일하면 **"기존 X와 합칠까요?"** 로 유도(Lint의 병합과 동일 로직 재사용).

### UI 상태 (라우팅 미리보기)
- 목적지별 그룹(기존/신규), 각 메모 체크·제외, "새로 만들기" 개별 토글.
- 확정 전에는 아무 변경도 커밋하지 않음.

## 6. 재합성 (프롬프트 & 실행 상세)

### 실행 모델
- **트리거:** C.4 "정리 실행" 즉시(사용자 요청 배치라 비용 통제).
- **그룹핑:** 선택 메모를 **목적지 위키별로 묶어 위키당 1 호출.**
- **백그라운드:** 위키 `markdown_status = .processing` → 완료 시 `.completed` + 재임베딩.

### 증분 재합성 프롬프트(형태 제안)
- system: "너는 개인 지식 위키의 유지관리자다. 기존 위키 페이지에 새 메모들을 **통합**하되, 단순 이어붙이기(append) 금지. 종합·재구성하라. 사실에 충실(환각 금지), 원문 세부(이름·숫자·URL) 보존. 사용자가 직접 편집한 부분은 존중. 새 정보가 기존 내용과 **모순되면 표시**. 출력은 JSON."
- user content:
  ```
  [기존 위키 페이지]
  {현재 markdown}

  [새로 추가된 메모 N개]
  - {메모1 요약/본문}
  - {메모2 …}
  ```
- 출력 JSON: `{ "markdown": string, "summary": string, "related_topics": string[] }`
  - `related_topics` → `wiki_wiki_link` 후보로 사용(기존 위키명과 매칭되면 백링크 생성).

### 새 위키 첫 종합
- 기존 페이지가 없으므로 초기 구성원들만으로 종합. 같은 JSON 스키마.

### 위키 페이지 MD 구조(권장)
```markdown
# {제목}
{종합 요약 2~4문장}

## 핵심 포인트
- …

## 관련 위키
- [[다른 위키]] …        ← wiki_wiki_link

## 구성 메모
- {메모 제목} (YYYY-MM-DD)  ← note_wiki_link, 클릭 시 정리본
```
- (선택) YAML 프론트매터(tags/updated/member_count) → 추후 동적 뷰.

### 비용/성능
- 전체 재합성은 누적 입력이 O(N²)로 폭증 → **반드시 증분.**
- `reasoning_effort: low`, `response_format: json`(현 `LunaMarkdownGenerator`와 동일).
- 1인 사용자 기준 절대 비용은 작음; 대규모/멀티토픽에서 목적지 상한으로 관리.

## 7. 채팅 검색 전략 (상세)

1. 질의 임베딩 → **위키 임베딩 우선 검색**(topN_wiki).
2. 위키 히트가 충분하면 위키 페이지를 컨텍스트로 답변, 출처=위키.
3. 부족하거나 구체 근거 필요 시 **구성 메모/개별 메모 드릴다운**(topN_note), 출처=메모.
4. 관련도 순 정렬 유지(기존 `relevantSources` 로직 확장).
5. 출처 칩에 **`위키`/`메모` 배지** + 클릭 시 각각 위키 상세/정리본 미리보기.
6. 둘 다 부족 → 웹 검색 폴백(구현됨).

## 8. Lint (유지보수, 상세)

| 검사 | 방법 | 결과 |
|---|---|---|
| 중복 위키 | 위키 임베딩/슬러그 유사도 ≥ T_merge | "합칠까요?" 제안 카드 |
| 모순 | 재합성 시 LLM이 표시한 conflict 수집 | 위키 상단 경고 |
| 고아/빈약 | `member_count ≤ 1` 또는 inbound link 0 | "정리/삭제 제안" |
| stale | 오래 갱신 안 됨 + 관련 새 메모 존재 | "업데이트 제안" |

- 트리거: 주기적 백그라운드 + 사용자가 위키 메뉴 열 때 가벼운 점검.
- 절대 자동 파괴 금지 → 항상 **제안 카드**(사용자 승인).

---

## 9. MCP (상세)

- 노출 범위: **위키 페이지(종합 MD)만.** raw/개별 메모/원본 파일 미노출.
- 도구 형태: 위키 검색(read) + 위키 페이지 read. (Karpathy가 언급한 qmd-as-MCP와 유사, 단 위키 한정)
- 전제: 위키 신선도(Lint), **공개/비공개 위키 플래그**로 권한 스코핑.
- 이유: 위키는 정제·종합된 고신호 + 프라이버시 안전 레이어라 외부 노출에 최적.

---

## 10. 신뢰 · 안전

- **사람 편집 보호:** 사용자가 위키 페이지를 편집하면 `markdown_edited = true` → 자동 재합성이 덮어쓰기 전 확인(정리본의 기존 로직을 위키로 확장).
- **되돌리기:** 재합성/승격은 조용한 버전 히스토리 + 원클릭 되돌리기(비개발자는 디버깅 못 함).
- **환각 억제:** 프롬프트 충실성 규칙, 구성 메모로 출처 추적 가능.
- **투명성:** "이 위키는 메모 N개로 만들어졌어요" + 구성 메모 링크 상시 노출.

---

## 11. 엣지 케이스

- **메모 삭제/언링크:** 소속 위키의 `member_count` 감소 → 필요 시 재합성(다음 승격/열람/lint 때). 구성원 0이면 고아 위키 → 삭제/보관 제안.
- **위키 삭제:** `note_wiki_link` 정리, 메모는 그대로(메모는 위키와 독립).
- **콜드스타트:** 메모 1~2개는 위키 없이 자연스러움. 사용자가 명시적으로 승격하면 1개로도 새 위키 생성 가능(명시적 의도).
- **대량 선택:** 미주입 200개 → 전체 선택/토픽 필터/추천 배치("이 12개는 '생산성'으로").
- **멀티멤버십:** "주입됨"은 최종 아님 — 다른 위키에 추가 가능, 각 메모에 소속 위키 배지.

## 13. 미결 질문 (Open Questions — 착수 전 확정 필요)

- **OW1. 토픽 체계:** (A) 완전 발현형 — AI가 자유 생성 + 사후 병합, vs (B) 반통제형 — 사용자 위키 목록을 정답 집합으로 삼고 새 위키는 명시적 승인. **잠정: B로 시작 → A 얹기.**
- **OW2. 위키 대표 임베딩:** 위키 페이지 자체 임베딩 vs 구성 메모 centroid. (매칭 품질/비용 트레이드오프)
- **OW3. 임계값:** T_match(매칭), T_merge(병합), N_max(멀티토픽 상한) 초기값 + 튜닝 방법.
- **OW4. 되돌리기 저장 방식:** 위키 MD 버전 스냅샷 vs git 유사 이력.
- **OW5. Lint 트리거 주기:** 시점·빈도·비용.
- **OW6. 자동 추천 강도:** 미주입 메모에 추천을 미리 체크할지, 배지만 보여줄지.
